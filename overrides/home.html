The problem

Scanners find it.
Nobody closes the loop.

A scanner reports hundreds of findings, and the numbers only grow. Matching today's report to last week's breaks as soon as someone adds a line above a finding. sarifix gives every finding an identity that survives edits, so you can say what is new, what is fixed and what is unchanged.

Core ideas

Three things you
configure once.

Scanners are entries in a YAML file. Identity comes from fingerprints. Trust comes from verification, which arrives with the fixing phases.

Scanners

Shipped

A name, the SARIF tool names to match, and a command. No code change to add a tool.

- name: checkov
  match: ["Checkov"]
  command: ["checkov", "-d", "{dir}",
    "-o", "sarif",
    "--output-file-path", "{outdir}"]

Fingerprints

Shipped

The tool's own hash if it has one, otherwise a hash of tool, rule, path and the flagged code.

partialFingerprints:
  sarifix/v1: fcadca11a498b6d6…

line numbers never count

Verification

Planned, phase 2

A fix ships only if the rescan shows the finding gone, nothing new, and your tests pass.

verify:
  commands: [["make", "test"]]
  require_no_new_findings: true

Quick start

From zero to a scan
in 3 commands.

You need Go 1.27 or newer, and whichever scanners your config calls on your PATH. Release binaries are signed with cosign if you prefer those.

{% include ".icons/material/book-open-page-variant-outline.svg" %} Full getting-started guide

  1. Install

    $ {{ install }}

  2. Check your config

    Start from the example in the repo and validate it.

    $ sarifix config validate --config examples/sarifix.yaml

  3. Scan

    One SARIF file per scanner, each result fingerprinted.

    $ sarifix scan

How it works

One pipeline.
Three stages ship today.

Phases 0 and 1 cover ingest, fingerprinting, the baseline diff, filtering, grouping and the report. The agent, verification and the other publish modes follow in phases 2 to 4.
